Automation Basics

Spotting the jobs worth automating, and describing one clearly enough that somebody can actually build it.

Why this matters

The same report, 240 times a year

Every weekday, someone in a Chennai office downloads two files, pastes them into a third, deletes four columns, and emails the result to six people. It takes 25 minutes. It has been done this way for three years.

About 100 hours a year, on copying and deleting.
What changes

You do not need to build it. You need to describe it well enough.

What you'll be able to do

By the end of this module

What can be automated

Rules, not judgement

Rules can be automated

If you can write the job as "when this happens, do exactly that", it can be automated. If you cannot, it cannot.

Automatable

Same input, same action

  • Move files that arrive into a dated folder
  • Email a report every Monday at eight
  • Flag any invoice over a set value
  • Copy fields from a form into a sheet
Not automatable

Requires a judgement

  • Decide whether a complaint deserves a credit
  • Choose which supplier to trust this quarter
  • Word a difficult message to a client
  • Decide when a rule should be broken

The three parts of any automation

1

A trigger

What starts it. A time, a file, an email, a form.

2

Steps

Exactly what happens, in order, with no choices.

3

Exceptions

What to do when reality does not match the rule.

4

A human

Who gets told when an exception happens.

Terms on this page: Trigger

Spotting a candidate

Four questions

Four questions that find one

Four yeses is a candidate

Frequent

Twice a week is 100 times a year. Twenty-five minutes each is a working fortnight.

Identical

If it varies, write down what varies. That is usually the exception list.

Mechanical

Copying, moving, renaming, filtering, sending. No decisions in the middle.

Describing it properly

Trigger, steps, exceptions

Describe it, do not build it

Most automation requests fail because the description is vague, not because the tool was wrong.

Copy this description prompt
Help me describe a manual process so somebody could automate it. Ask me one question at a time until you have: the trigger, every step in order, every exception, and who should be told when an exception happens. Do not suggest tools yet. Start with your first question.
One question at a time is what makes this work.
Why this works
  • Interviewing you finds steps you would not have written down.
  • "No tools yet" keeps the focus on the process.
  • You end up with a specification, not a wish.

Vague request, clear request

What usually gets asked
  • "Can we automate the daily report?"
  • Nobody knows which files, which columns, or who receives it.
  • Three meetings later it is still being discussed.
What gets built
  • "Every weekday at 07:00, take the two files from this folder..."
  • "...remove columns D, F, H and K, merge on order number, email to this group."
  • "If either file is missing at 07:15, email me and stop."

The second one can be built by somebody who has never seen your job. That is the whole test.

What must stay manual

Where automation hurts

Where automation hurts

1
Automating an approval
The approval was the control. Automating it removes the only place a human looked.
2
Auto-sending to customers
One bad input becomes 400 wrong emails before anybody notices.
3
Automating a broken process
You now do the wrong thing reliably, at speed, without anyone watching.
4
Hiding the exceptions
If nobody is told when it fails, it fails silently for months.
5
Automating something one person understands
When they leave, nobody knows what it does or how to stop it.

The rule about approvals

Automate the work. Never automate the check on the work.

If a step exists so that a human looks at something, that step is the point.

  • Payments — a person approves.
  • Customer messages — a person sends.
  • Anything irreversible — a person decides.

Describe one real job

Do this now: describe one job

  1. Pick the job you do most often that has no thinking in it.
  2. Run the interview prompt and answer its questions honestly.
  3. Add every exception you can remember from the last year.
  4. Send the result to [COMPANY INPUT NEEDED: who handles automation requests].
Copy this prompt
Interview me one question at a time to document a manual process for automation. I need: the trigger, the steps in order, every exception, and who is told when an exception happens. Do not suggest tools. Do not ask for real data. Begin.
Twenty minutes of questions produces something buildable.

Exceptions are the hard part

Copy this exception prompt
Here is a process description. List every way this could go wrong in practice: missing input, wrong format, duplicate, late arrival, partial data, and anything else. For each, suggest what the automation should do instead of guessing. One line each.
Most automations fail on the cases nobody listed.
What comes back
  • Ten to fifteen failure cases, several you had not considered.
  • A suggested safe behaviour for each, usually "stop and tell a human".
  • The list that turns a fragile script into a reliable one.

Three rules for anything running

What must never be in the description

Describing a process needs the shape of the data, never the data itself.

Column names and formats are enough for anyone to build from.

  • Real customer records used as the example
  • Passwords, API keys or shared login details
  • Internal system addresses posted outside the company
  • Live financial figures used to illustrate a step

Is it worth automating?

Does this cost more than a day a year?
Yes

Write it up

Twenty-five minutes a day is a hundred hours a year. Even a rough automation that handles the normal case pays for itself in weeks.

No

Leave it alone

A monthly ten-minute job costs two hours a year. Automating it costs more than that to build, document and maintain.

The automation rule

If you cannot write it as rules with no choices in the middle, it is not ready to automate.

The writing is the work. Building is usually the easy part afterwards.

  • Rules — automate.
  • Judgement — keep.
  • Exceptions — always to a human.

Recap

Automation on one screen

Rules can be automated

"When this happens, do exactly that." If you cannot write it that way, it is not ready.

Four questions find a candidate

Frequent, identical, transferable, mechanical. Four yeses and it is worth writing up.

Describe, do not build

Trigger, steps in order, exceptions, and who gets told.

Exceptions are the real work

Missing files, duplicates and wrong formats are where things fail silently.

Never automate the check

If a step exists so a person looks, that step is the whole point.

Someone owns it, someone can stop it

Named owner, documented purpose, and an off switch anyone can use.

Automate the copying. Keep the judgement. Send every exception to a human.

Glossary

Words used in this module

Trigger
What starts an automation: a time, a file arriving, an email, a form submission.
Exception
A case where reality does not match the rule. The automation should stop and tell someone.
Specification
A description clear enough that somebody who has never seen your job could build it.
Owner
The named person responsible for an automation and for switching it off.
Judgement
A decision needing context a rule cannot see. Never automated.
Prompt
Everything you type in: your process description and the constraints.
